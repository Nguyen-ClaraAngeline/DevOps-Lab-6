# ADR-001: Stack, transaction boundary and invariants

Status: Accepted · Date: 2026-11-10

## Context
FulfillOps accepts orders over HTTP, reserves limited stock and fulfils orders asynchronously. Clients
retry, several API replicas share one database, and workers can crash mid-job. We must never oversell,
never create two orders for one idempotency key, and never lose an order acknowledged with 202.

## Decision 1: Stack
- Language: Python 3.12 (API and worker). The public checker and probe are Python too.
- Database: PostgreSQL 16.
- Queue: a `jobs` table in the same Postgres, not Redis/RabbitMQ.
- Migrations: plain SQL files in `db/migrations/`, applied by `db/migrate.sh`, tracked in `schema_migrations`.

Why a work table: the order, the stock decrement and the job must commit atomically. With a broker,
"commit then publish" can lose the message on a crash, and "publish then commit" can process a rolled-back
order. With a jobs table, enqueueing is one more INSERT in the same transaction. Cost: polling latency and
more load on Postgres, acceptable at this scale.

## Decision 2: Transaction boundary
One database transaction in the API:
1. INSERT into `idempotency_keys` ON CONFLICT DO NOTHING. On conflict, compare `payload_hash`: same hash
   returns the original order_id with 202, different hash returns 409 IDEMPOTENCY_CONFLICT.
2. Sum quantities per SKU and process SKUs in sorted order (fixed lock order, no deadlocks).
3. For each SKU run `UPDATE products SET available = available - q WHERE sku = s AND available >= q`.
   Zero rows changed: ROLLBACK and return 409 OUT_OF_STOCK (this also undoes the key insert).
4. INSERT the order (with total_cents), its items and a queued job, set `idempotency_keys.order_id`,
   COMMIT, return 202.

The boundary ends at COMMIT. Fulfilment is driven only by the `jobs` row.
The worker has its own boundary: claim with FOR UPDATE SKIP LOCKED and set a lease; do the work; then in
one transaction set `orders.status='completed'` (guarded) and `jobs.state='completed'`.

## Invariants
| # | Invariant | Enforced by |
|---|---|---|
| I1 | `available >= 0` always | CHECK constraint + conditional UPDATE |
| I2 | accepted quantity never exceeds initial stock | atomic conditional decrement in the order transaction |
| I3 | one idempotency key maps to at most one order | PK on `idempotency_keys.key`, ON CONFLICT DO NOTHING |
| I4 | same key with different payload never silently succeeds | normalized (sorted-key) payload hash, 409 |
| I5 | every committed order has exactly one job | order and job inserted in one transaction; `jobs.order_id` is PK |
| I6 | a failed request leaves no trace | single transaction, rollback on any failure |
| I7 | a job is held by at most one live worker | SKIP LOCKED + lease (`locked_until`) |
| I8 | at-least-once delivery, exactly-once effect | lease recovery + guarded `WHERE status <> 'completed'` |
| I9 | retries are bounded; exhausted jobs go dead, order failed, no restock | `attempts` vs `max_attempts` |
| I10 | API replicas hold no state | all state in Postgres |

## Consequences
- Good: one source of truth, no dual-write problem, simple Compose/CI/Kubernetes setup.
- Bad: Postgres is both store and queue, so a DB outage stops everything (reported by /health/ready).
  Workers poll, so latency is bounded by the poll interval.
- Failed orders are not restocked (spec requirement).

## Alternatives rejected
- Redis/RabbitMQ: dual-write problem, extra component to run and secure.
- SERIALIZABLE isolation: more retry logic, no extra guarantee here.
- Check-then-update stock in app code: race condition.
- Per-SKU advisory locks: the row lock from UPDATE already does this.
